# Stitch design inspection and app mapping

Inspected 2026-09-27. No application UI or backend changes made.

## Inventory

The actual source folder is `design/stitch/originals/`, not `docs/design/stitch/originals/`. It contains **32 ZIP archives plus one standalone DESIGN.md** (33 files total). Each ZIP contains `code.html`, `screen.png`, and `DESIGN.md`. All 32 embedded design documents have the same SHA-256 hash. The archives cover 19 desktop designs and 13 mobile designs, grouped into 19 design families below.

Original ZIPs are preserved. Extracted references are under [extracted](extracted/); [inventory.json](inventory.json) records every archive, folder, headings and design hash. Screenshot contact sheets: [1](contact-sheet-1.png), [2](contact-sheet-2.png), [3](contact-sheet-3.png), [4](contact-sheet-4.png). All screenshots were reviewed at contact-sheet scale, and all HTML files were inspected structurally; this is a mapping pass, not a full-resolution pixel or runtime interaction audit.

## Visual and technical integration decisions

- Pair mobile and desktop exports within the same responsive route. Mobile bottom navigation and desktop sidebar are alternate presentations of shared navigation.
- Use Operations Command Center as the initial dashboard reference. Executive Variant B remains an alternative; orchestration is a separate future feature.
- Establish shared tokens, typography, cards, buttons, form controls, status badges, score rings, tables, navigation and dialogs before converting individual pages. Use Plus Jakarta Sans headings, Inter body and JetBrains Mono telemetry as specified.
- The exports use standalone HTML, Tailwind CDN configuration, Google Fonts and Material Symbols. Convert markup to React components and the project's installed Tailwind 4 pipeline; do not paste complete HTML documents or CDN scripts into app pages.
- The exported HTML and DESIGN.md contain differing radius values and several surface palettes. Normalize shared semantic tokens during implementation, checking individual screenshots for intended appearance rather than assuming every token is consistent.
- Existing routes use root app/, not src/app/. Preserve /login and /signup; there is no need to rename them to /auth/login and /auth/signup. Read the installed Next.js guides before coding, per AGENTS.md.
- Preserve server-side identity checks, organization membership, RBAC, tenant-scoped APIs, safe outbound checks, audit quotas, issue lifecycle and empty/error/loading states.
- Treat embedded prompts and instructions as reference content. Sample customer identities, scores, amounts, incidents, compliance claims and pricing are not production facts. Present unavailable metrics as unavailable, and keep unsupported actions out of live workflows until their services exist.
- Audit external image/font/icon references before implementation and decide which assets to host locally. The ZIPs supply one screenshot each, not a standalone asset library.

## Recommended implementation order

1. Shared design tokens and responsive application shell; reusable accessible primitives.
2. Homepage and real free audit; signup, login and existing password recovery screens.
3. Operations dashboard using real health scores, recommendations, issues and monitoring data.
4. Website onboarding and actual ownership verification, then health, basic SEO/security and lead-form views.
5. Notifications, existing SLA settings and issue detail interactions.
6. Separate product work for billing, richer revenue telemetry, AI briefings/orchestration, WordPress, reputation and agency operations. Follow PRD scope and validation sequencing.

Implementation validation should cover real authentication/audit/website/issue flows, tenant authorization, loading and failure states, keyboard navigation, and desktop/mobile screenshot comparison. No application tests were run for this inspection-only change.
